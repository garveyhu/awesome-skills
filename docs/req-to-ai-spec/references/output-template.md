# 输出模板：AI友好型需求规格文档

本文件定义每份生成的规格文档必须遵循的标准结构。Skill在生成文档时读取本模板。

**语言规则：** 输出文档的语言与用户描述需求时使用的语言一致。用户用中文则全文中文，用英文则全文英文。YAML元数据的key保持英文。

---

## 文档结构

````markdown
---
generated: YYYY-MM-DD
source_materials: text | text+screenshots | text+screenshots+codebase
workspace: "/path/to/codebase" 或 "none"
skill_version: req-to-ai-spec v1
---

# <需求标题>

## 概述

<2-3句话：目标用户是谁、新增或变更什么能力、为什么要做>

## 术语表

| 术语 | 含义 |
|------|------|
| <领域术语> | <通俗解释> |

## 全局约束

- <适用于以下所有Task的约束条件>

## 实现顺序

1. **Task 1** -- <一句话说明为什么排第一>
2. **Task 2** -- <一句话说明，如：依赖Task 1的表结构变更>
3. ...

## Task 1: <动词短语标题>

**目标**：<一句话描述交付成果>

**验收标准**：
- [ ] <可验证的标准——能做yes/no判断的测试或检查>
````

## 逐章节写作指引

### YAML元数据

| 字段 | 内容 | 正确示例 | 错误示例 | 常见错误 |
|------|------|----------|----------|----------|
| `generated` | 生成日期，ISO格式 | `2026-03-18` | `3月18日` | 使用非标准日期格式 |
| `source_materials` | 实际消费的输入类型 | `text+screenshots` | `混合` | 自造不在枚举中的分类；没探索代码却标了codebase |
| `workspace` | 探索的代码库绝对路径，或`"none"` | `"/Users/dev/project"` | `"项目"` | 写相对路径；实际读了代码却漏填 |
| `skill_version` | 固定字符串，用于溯源 | `req-to-ai-spec v1` | `v1` | 修改格式或漏掉skill名前缀 |

### 需求标题（`# <需求标题>`）

- **内容**：整个需求集的简洁名称。源材料有明确标题就复用，没有就提炼一个。
- **正确**：`# 移动端医生工作台：角色切换与筛查预填写`
- **错误**：`# 新功能` 或 `# 需求`
- **常见错误**：太笼统；把实现细节塞进标题。

### 概述

- **内容**：恰好2-3句。第1句：用户是谁。第2句：做什么。第3句：为什么做（业务价值或解决的痛点）。
- **正确**："目前筛查医生只能通过管理端后台操作病例。本需求为移动端新增医生工作台和角色切换能力，让医生可以在手机上进行筛查预填写和随访管理。目标是去除桌面端依赖，缩短筛查流转时间。"
- **错误**："给医生加一些功能。会有新接口和新页面。这个很重要。"
- **常见错误**：写超过3句；复述Task列表而非提供上下文；漏掉"为什么做"。

### 术语表（可选）

- **何时包含**：需求引入了领域特定术语、缩写，或AI编码代理凭通用训练无法理解的概念时。
- **内容**：两列表格。左列术语，右列通俗解释。
- **正确**：`| institution_staff_info | 将手机号关联到员工角色和机构的数据表 |`
- **错误**：`| API | 应用程序编程接口 |`（普遍已知，不需要）
- **常见错误**：收录通用编程术语；遗漏真正的领域术语；定义了术语但在Task中从未使用。

### 全局约束（可选）

- **何时包含**：仅当某条约束适用于每一个Task时。如果只适用于一个Task，放到那个Task的核心规则里。
- **内容**：跨领域规则的要点列表：安全策略、接口规范、共享数据格式规则、性能要求。
- **正确**：`- 所有新增的医生端接口必须复用现有移动端JWT认证机制，携带有效token`
- **错误**：`- 遵循最佳实践`（不可执行）
- **常见错误**：把Task专属的规则堆到这里；写愿景式陈述而非可执行的规则。

### 实现顺序（可选）

- **何时包含**：多个Task且顺序有影响时（如先做数据迁移再做接口、先做公共工具再做消费者）。
- **内容**：编号列表，每项引用Task并附一句理由。
- **正确**：`1. **Task 1** -- 提供角色查询接口，Task 2和3都依赖它`
- **错误**：`1. Task 1 -- 先做这个`（无理由）
- **常见错误**：只有一个Task时还写这个章节；给了顺序但不解释为什么。

### Task单元字段

#### Task标题（`## Task N: <动词短语标题>`）

- **内容**：描述交付物的动词短语。以动词开头："新增"、"实现"、"替换"、"重构"。
- **正确**：`## Task 1: 新增角色查询与切换接口`
- **错误**：`## Task 1: 角色相关` 或 `## Task 1: 接口`
- **常见错误**：用名词短语而非动词短语；标题过长变成段落。

#### 目标

- **内容**：一句话。这个Task的唯一交付成果。
- **正确**："提供一个查询接口，返回当前用户的角色（医生或家长）及关联的机构信息。"
- **错误**："做一个接口。"（太模糊）或一整段话（太长）。
- **常见错误**：复述标题；写实现步骤而非交付成果。

#### 前置条件

- **内容**：开始这个Task前必须已成立的条件。想：必须已存在的数据表、已完成的其他Task、环境配置。
- **正确**：`- 机构员工表存在，包含字段：phone、staff_type、institution_id、create_time`
- **错误**：`- 系统应该准备好`
- **常见错误**：有真实依赖时留空；列出"一台电脑"之类显而易见的东西。

#### 核心规则

这是最重要的章节。每条规则必须**明确且无歧义**——应直接对应一个代码分支或一个可测试的行为。

**正确示例：**
```
1. 根据当前登录用户的手机号查询机构员工表；如果恰好存在一条 staff_type=DOCTOR 的有效记录，则该用户具备筛查机构医生身份
2. 如果手机号匹配到零条记录，仅返回 role=PARENT
3. 如果手机号匹配到多条记录，取 create_time 最新的一条并记录警告日志
```

**错误示例：**
```
1. 检查用户是不是医生
2. 处理找不到的情况
3. 适当处理重复数据
```

好的示例无歧义——每条规则对应一个代码分支。坏的示例含糊不清，"检查"、"处理"、"适当"让AI无法确定具体行为。

- **内容**：编号列表。每项是一条精确指令。使用表名、字段名、HTTP方法、状态码——凡是能消除歧义的都要写。
- **常见错误**：用模糊动词（"处理"、"管理"、"操作"）却不说明具体行为；多个分支条件合并到一条规则；漏掉else分支。

#### 边界与异常

- **内容**：边界情况及处理方式的要点列表。想：空输入、空列表、并发修改、权限失败、数据迁移怪异行为。
- **正确**：`- 如果 institution_id 指向一个已软删除的机构，则视该员工记录为无效，降级为 role=PARENT`
- **错误**：`- 优雅地处理错误`
- **常见错误**：完全省略这个章节；用更模糊的语言复述核心规则；对可能发生的情况写"不应该发生"。

#### 验收标准

- **内容**：复选框列表。每项是一个具体的、可验证的测试。检查者（人或CI）必须能对每条做出yes/no判断。
- **正确**：`- [ ] 以医生手机号调用角色查询接口，返回200且body包含 role=DOCTOR、institution_id、institution_name`
- **错误**：`- [ ] 接口能正常工作`
- **常见错误**：写主观标准（"足够快"、"用户友好"）；照搬核心规则而非转化为测试视角。

#### 依赖

- **内容**：`无` 或逗号分隔的Task编号（如`Task 1, Task 3`）。
- **正确**：`Task 1`（确实需要Task 1的输出时）
- **错误**：`所有前置任务`（太模糊，请具名）
- **常见错误**：循环依赖；标注实际不存在的依赖；Task重排后忘记更新。

## 条件包含规则

以下章节为**可选**，不适用时必须完全省略（不要留空章节）：

| 章节 | 包含条件 | 省略条件 |
|------|----------|----------|
| 术语表 | 需求中出现领域专有术语 | 所有术语为常识 |
| 全局约束 | 某条规则适用于每一个Task | 约束仅针对特定Task |
| 实现顺序 | 多个Task且顺序有影响 | 单Task，或Task之间互相独立 |

## 质量检查清单

定稿前验证：

1. **每条核心规则都无歧义** -- 两个不同的开发者读完会写出相同的分支逻辑吗？
2. **无孤儿引用** -- 依赖和实现顺序中提到的每个Task都确实存在。
3. **验收标准可测试** -- 每条都是yes/no判断，非主观评价。
4. **可选章节是省略而非留空** -- 不要出现`## 术语表`下面没有表格行的情况。
5. **文档自包含** -- AI代理仅读本文档就能实现每个Task，无需额外澄清（代码探索除外）。
