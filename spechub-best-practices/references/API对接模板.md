# API 对接规约模板

适用场景：前后端联调、微服务间接口对接、第三方 API 封装交接。

在通用模板（`通用模板.md`）基础上，API 对接规约需要额外的特有内容。

---

## README.md 补充约定

API 对接的 README 在通用模板基础上，"通用约定"部分应包含：

````markdown
## 通用约定

### 环境与基础地址

| 环境 | 基础地址 |
|------|---------|
| 开发 | https://dev-api.example.com |
| 测试 | https://test-api.example.com |

### 鉴权方式

请求头：`Authorization: Bearer <token>`

（说明不同端的 token 体系差异。）

### 通用响应包装

所有接口返回统一包装：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": { ... }
}
```

错误时：

```json
{
  "code": 500,
  "msg": "具体错误信息",
  "data": null
}
```

> 消费方应优先判断 `code !== 200` 来处理异常，`msg` 可直接用于 toast 提示。

### 分页约定

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| pageNum | number | 否 | 1 | 页码，从 1 开始 |
| pageSize | number | 否 | 10 | 每页条数，最大 100 |

分页响应：

```json
{
  "rows": [...],
  "total": 42
}
```

### 时间格式

所有时间字段为 `yyyy-MM-dd HH:mm:ss`，时区 Asia/Shanghai。
纯日期字段为 `yyyy-MM-dd`。

### null 与空值约定

- object 无数据：`null`
- array 无数据：`[]`
- string 无数据：`""`

消费方据此区分"没有"和"有但为空"。
````

## 01-链路总览.md 模板

回答："有哪些页面？每个页面调用哪些接口？按什么顺序？状态如何流转？"

这个文件让消费方 AI 先建立全局心智模型，再去看单个接口细节。没有这个视角，AI 会孤立实现每个接口，遗漏它们之间的关联。

````markdown
# <模块> 链路总览

更新时间：YYYY-MM-DD

## 1. 总体概览

本次对接涉及 N 条链路：
1. 链路 A
2. 链路 B
3. ...

## 2. 页面与接口对应关系

### 2.1 <页面名称>

**目标：**
- 该页面要实现什么

**接口调用顺序：**
1. `GET /api/xxx` — 获取初始数据
2. 用户操作（选择/填写/点击）
3. `POST /api/yyy` — 提交数据
4. 成功后跳转到 <下一页面>

**关键变化：**
- 相比旧版本的改动

**注意事项：**
- 应该：...
- 禁止：...（以及为什么）

<!-- 每个页面重复以上结构 -->

## 3. 状态流转

> 必须用结构化方式写出，不要只用自然语言描述。

```
[PENDING] --POST /api/approve--> [ACTIVE]
[PENDING] --POST /api/reject--> [REJECTED]
[ACTIVE]  --POST /api/disable--> [DISABLED]
```

| 状态值 | 含义 | 展示建议 | 允许的操作 |
|--------|------|---------|-----------|
| PENDING | 待处理 | 黄色标签 | 编辑、删除 |
| ACTIVE | 已生效 | 绿色标签 | 下架 |

## 4. 角色与上下文

> 如果系统有多种角色或上下文切换，必须说明清楚。
> 角色决定了哪些接口可用、数据范围如何隔离。

### 4.1 <角色 A>
- 接口路径、数据范围、特殊限制

## 5. 推荐开发顺序

1. ...
2. ...

## 6. 重点注意事项

### 6.1 <标题>
- **问题**：可能踩的坑
- **正确做法**：应该怎么做
- **原因**：为什么

## 7. 完整调用链路

> 按实际调用的先后顺序列出全部接口，方便消费方逐个对接。

1. `GET /api/first` — 用途
2. `POST /api/second` — 用途
````

## 02-详细接口说明.md 模板

最关键的文件。每个接口都是一份完整的、自包含的合约，让消费方 AI 无需提问即可实现。

````markdown
# <模块> 详细接口说明

更新时间：YYYY-MM-DD

## 1. 通用说明

（引用 README 中的约定，补充本模块特有的。）

## 2. 枚举定义

> **这是整个规约中最容易遗漏、对消费方 AI 影响最大的部分。**
> 缺少枚举表 = 消费方 AI 无法渲染下拉框、单选按钮、状态标签，只能猜。
> 规则：每一个值不是自由输入的字段，都必须有枚举表。

### status 状态

| 值 | 含义 | 展示建议 |
|----|------|---------|
| UP | 上架 | 绿色标签 |
| DOWN | 下架 | 灰色标签 |

### sex 性别

| 值 | 含义 |
|----|------|
| 1 | 男 |
| 2 | 女 |

<!-- 列举本模块所有枚举类型 -->

## 3. 接口总览

| # | 方法 | 路径 | 用途 | 鉴权 |
|---|------|------|------|------|
| 1 | GET | /api/xxx | 获取列表 | App 登录态 |
| 2 | POST | /api/yyy | 保存数据 | 管理端登录态 |

## 4. 接口详情

---

### 4.1 <接口名称>

**使用场景：** 什么时候调用，对应链路总览中的哪个步骤。

**请求：**

`POST /api/xxx`

Content-Type: `application/json`

**请求参数/请求体：**

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| name | string | 是 | - | 名称，最大 50 字符 |
| type | number | 是 | - | 类型，见 [typeCode 枚举](#typecode) |
| items | array\<ItemDTO\> | 是 | - | 子项，至少 1 项 |

**ItemDTO：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| productId | string | 是 | 产品 ID |
| quantity | number | 是 | 数量，最小 1 |

**请求示例：**

```json
{
  "name": "示例配置",
  "type": 1,
  "items": [
    { "productId": "prod_001", "quantity": 2 }
  ]
}
```

**响应 `data` 字段：**

| 字段 | 类型 | 可为null | 说明 |
|------|------|---------|------|
| id | number | 否 | 主键 |
| status | string | 否 | 见 [status 枚举](#status-状态) |
| parentInfo | object\<ParentDTO\> | 是 | 无数据时为 null |
| tags | array\<string\> | 否 | 无数据时为 `[]` |

**响应示例：**

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "id": 42,
    "status": "UP",
    "parentInfo": null,
    "tags": ["tag1"]
  }
}
```

**常见错误：**

| msg | 触发条件 | 消费方处理建议 |
|-----|---------|--------------|
| "名称不能为空" | name 未传 | 表单校验拦截 |
| "数据不存在" | id 无效 | toast 并返回列表 |

**后端行为说明：**
- 忽略/覆盖的字段：`computedField`（后端自动计算，传了也无效）
- 副作用：保存后自动触发 xxx
- 幂等性：重复调用会 xxx
````

## API 对接自检补充

在通用自检清单（见 `通用模板.md`）基础上，API 对接还需确认：

- [ ] 鉴权方式已说明（header 名、token 类型）
- [ ] 响应包装结构已说明
- [ ] 分页约定已说明
- [ ] 时间格式已显式声明
- [ ] null 与空值约定已说明
- [ ] 每个非自由输入字段都有枚举表
- [ ] 每个接口至少有一个完整 JSON 响应示例（含外层 wrapper）
- [ ] POST/PUT 接口有完整 JSON 请求体示例
- [ ] ID 字段类型明确（number 还是 string）
- [ ] 包含序列化 JSON 的 string 字段已说明解析后结构
- [ ] "后端会覆盖"的字段已标注
- [ ] 状态机已显式写出
- [ ] 完整调用链路已列出
