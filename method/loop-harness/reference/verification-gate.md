# 验证门设计（命门①·怎么为不同任务定「可执行的二元成功检查」）

> loop 最容易翻车的地方是**注水**——agent 声称做完其实没做。唯一的根治是：**别让 agent 评判自己的产出，让一个外部客观检查评判**。研究实锤：LLM-as-judge 当唯一门，单个无意义 token 就能骗到 80% 假阳性。所以**每个 loop 任务立项时就得定一个可执行的二元成功判据**，agent 报它的结果、不报自评。

## 一条好验证门的标准
- **可执行**：跑一条命令/脚本/测试就出结果，不靠人肉看。
- **二元**：过 / 不过（或一个客观数值 vs 阈值），不是「感觉还行」。
- **抗自评**：结果来自 agent 之外（exit code / 测试 / 真测产物 / 第三方），agent 不能靠嘴改。
- **贴真实输出**：日志里贴检查的原始输出，不贴「我觉得过了」。

## 按任务类型选验证门（实战速查）

| 任务类型 | 可执行验证门 | 注意 |
|---|---|---|
| 代码/重构 | 测试套件 exit 0 + 类型检查（tsc/pyright）+ 编译过 | commit 前全套必过·别只跑改动的测试 |
| 修 bug | 先写复现测试（红）→ 修 → 测试转绿 | 没复现测试 = 没验证·配 systematic-debugging |
| 出图/出视频/媒体 | 真调 API 出真产物 + 客观指标（分辨率/freezedetect 死帧/抽帧肉眼/响度） | 不信「应该生成了」·真跑真看 |
| 数据/计算 | 数值实算对照已知值 / schema 校验 | 别信 LLM 心算·python 实算 |
| 文档/事实源同步 | 与代码事实源 diff / grep 残留旧标记 / doctor 无漂移 | 防文档与代码漂移 |
| 调研/对标 | source-backed（每条结论带可核链接）+ 对抗评估员复核 | 防编造·LLM-judge 只当补充不当唯一门 |
| 性能 | benchmark 实测前后对照 | 别信「应该更快」 |

## 多智能体当验证门的正确姿势（对抗验证 RLAC）
- **建造员**做事 → **对抗评估员**专门挑刺/找失败模式（默认怀疑·要证据·引文件行）→ 你**客观核**评估员的指控（别轻信 agent·该 python 实算就实算）。
- **铁律**：对抗评估员/LLM-judge 是**客观 gate 的补充**，**绝不当唯一验证门**（单 token 可骗 80% 假阳）。最终拍板靠可执行检查。
- 实战价值：100 轮里对抗评估员第一刀就揪出文档与代码反向漂移、过冲数值超标、shelf-ware（建了没人用）——都被随后的代码实核证实。**「派对抗评估员防注水」机制真有效**。

## 验证门定不出来怎么办
说明北极星太模糊（「让它更好」不是目标）。先 [`brainstorming`](../../brainstorming/SKILL.md) 把「什么算做对了/逼近了」逼出一个可检查的判据，再开 loop。**没有验证门的 loop = 注水温床**，不如不开。
